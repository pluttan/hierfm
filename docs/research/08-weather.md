# 08. Температура по узлам иерархий

Дата: 2026-10-19. Метод: проверка API запросами, чтение страниц документации, пробные загрузки на маке.
Все числа про API и модели получены из запросов этого дня. Что не проверено, помечено словом "не проверено".

## 1. Итог

- Источник факта: Open-Meteo Historical Weather API, модель `era5_land` (реанализ ERA5-Land, 9 км, час). Ключ не нужен. Работает, проверено.
- Источник прогноза задним числом: Open-Meteo Previous Runs API, поле `temperature_2m_previous_day1`. Это прогноз, выпущенный за 24 часа до часа события. Для модели `ecmwf_ifs025` ряд начинается с марта 2024 года, для `gfs_global` с мая 2021 года.
- Historical Forecast API для честного опыта не подходит. Он склеивает первые часы каждого прогона, то есть почти анализ, а не прогноз на сутки.
- Таблица точек: 146 узлов, 215 уникальных точек (110 в России, 105 в Европе). Файл `data/meta/weather_points.csv`.
- Главный лимит: бесплатный ключ даёт 10000 условных вызовов в сутки. Один год по одной точке стоит около 26 вызовов. Весь план (факт и прогноз) занимает несколько суток. Скрипт возобновляется сам.
- Запасной источник факта: Copernicus CDS ERA5 (нужна регистрация, описание в разделе 7).

## 2. Зачем нужна температура в статье

Температура входит в оба метода статьи.

- Метод A. Априорная ковариация ошибок использует корреляцию температуры между узлами. Для неё нужен факт за годы, чтобы оценить устойчивую связь между узлами.
- Метод B. Перестановка Шааке (вариант `schaake_temp` в `configs/ru.yaml`) выбирает исторические дни, похожие по прогнозу температуры на целевой день. Для неё нужен прогноз температуры на день испытания. Факт здесь даёт утечку: прогноз модели нагрузки не знал бы фактической температуры.
- Нагрузка зависит от температуры нелинейно. Для иерархий это изучено в работе Hong, Wang, White (2015): выбор метеостанций для каждого узла сильно влияет на точность. Они отмечают, что для иерархии вручную подобрать станции каждому узлу нельзя, и часто берут одинаковое число станций на уровне. Мы делаем так же: города по населению. Hong T., Wang P., White L. Weather station selection for electric load forecasting. International Journal of Forecasting, 31(2), 286-295, 2015. DOI 10.1016/j.ijforecast.2014.07.001. Найдена в поиске, текст не читался.
- Развитие метода выбора станций: Moreno S., Sánchez-Úbeda E.F., Muñoz A. Rethinking weather station selection for electric load forecasting using genetic algorithms. International Journal of Forecasting, 36(2), 695-712, 2020. Найдена в поиске, текст не читался.

## 3. Источники без ключа

### 3.1. Open-Meteo Historical Weather API (факт)

- Адрес: `https://archive-api.open-meteo.com/v1/archive`.
- Параметры: `latitude`, `longitude`, `start_date`, `end_date`, `hourly=temperature_2m`, `timezone=UTC`, `models=era5_land`.
- Проверка 2026-10-19: ответ получен для Москвы, Копенгагена, Тромсё, Палермо, Сочи, Владивостока. Модели `era5_land`, `era5`, `best_match` дают по 72 значения за трое суток без пропусков.
- Разница моделей на одной точке до 1 градуса (Тромсё, 12 января 2024: `era5_land` 0.6, `era5` 1.6, `best_match` 0.0). Поэтому модель надо фиксировать. Мы фиксируем `era5_land`.
- Без параметра `models` Open-Meteo выбирает источник сам (`best_match`). В Европе он может смешивать ERA5-Land и другие наборы. Ряд станет неоднородным. Параметр `models` обязателен.
- Запаздывание: данные отстают от текущей даты примерно на 5 суток. Скрипт берёт конец периода на 7 суток раньше сегодняшней даты.
- Последний час, который получили 2026-10-19: 2026-10-12 23:00 UTC. Это подтверждает запаздывание.
- Лицензия данных: CC BY 4.0, нужна ссылка на Open-Meteo. Бесплатный доступ только для некоммерческого использования.
- Как цитировать: Zippenfenig P. Open-Meteo.com Weather API. Zenodo, 2023. DOI 10.5281/zenodo.7970649. Проверено поиском.
- Сам реанализ: Muñoz-Sabater J. и др. ERA5-Land: a state-of-the-art global reanalysis dataset for land applications. Earth System Science Data, 13(9), 4349-4383, 2021. DOI 10.5194/essd-13-4349-2021. Проверено поиском. Разрешение 9 км.
- ERA5: Hersbach H. и др. The ERA5 global reanalysis. Quarterly Journal of the Royal Meteorological Society, 146(730), 1999-2049, 2020. DOI 10.1002/qj.3803. Проверено поиском. Разрешение 31 км.

### 3.2. Лимиты бесплатного доступа

Источник: страница open-meteo.com/en/terms, прочитана 2026-10-19.

| Период | Лимит |
|---|---|
| минута | 600 вызовов |
| час | 5000 вызовов |
| сутки | 10000 вызовов |
| месяц | 300000 вызовов |

Вызов считается дробно. Страница тарифов (open-meteo.com/en/pricing) приводит правило: вызов стоит больше единицы, если в нём больше 10 переменных или период длиннее двух недель. Пример страницы: две недели и 15 переменных стоят 1.5 вызова, четыре недели стоят 3.0 вызова. Точной формулы страница не даёт.

Для одной переменной мы принимаем оценку: стоимость равна числу дней, поделённому на 14. Один календарный год стоит около 26 вызовов. Оценка не проверена по счётчику сервера. Подтверждение или опровержение даёт запись в разделе 5 (на каком вызове сработал суточный лимит).

Итоговая стоимость плана при 215 точках:

| Набор | Дней | Вызовов на точку | Всего |
|---|---|---|---|
| факт 2018-01-01 .. 2026-10-12 | 3207 | около 229 | около 49000 |
| прогноз `ecmwf_ifs025`, 2024-03-01 .. 2026-10-18 | 962 | около 69 | около 14800 |
| прогноз `gfs_global`, 2021-05-01 .. 2026-10-18 | 2018 | около 144 | около 31000 |

Вывод. Факт и прогноз IFS занимают около 64000 условных вызовов. Это не меньше семи суток при лимите 10000. Прогноз GFS добавляет ещё три-четыре суток. Месячный лимит 300000 не мешает.

### 3.3. Historical Forecast API (не подходит как прогноз)

- Адрес: `https://historical-forecast-api.open-meteo.com/v1/forecast`.
- Документация (прочитана 2026-10-19): ряд собран из первых часов каждого прогона. Для полного горизонта нужен другой интерфейс, Single Runs API.
- Для модели ICON и других данные с ноября 2022 года, для ECMWF IFS HRES с января 2017 года (по таблице страницы).
- Документация предупреждает: ряд не годится для длинных рядов из-за смен версий моделей.
- Вывод. Первые часы прогона близки к анализу. Использовать их как "прогноз на сутки вперёд" нельзя. Это нарушило бы честность опыта.

### 3.4. Previous Runs API (подходит)

- Адрес: `https://previous-runs-api.open-meteo.com/v1/forecast`.
- Поле `temperature_2m_previous_day1` равно значению, которое модель предсказала за 24 часа до часа события. Поля `_previous_day2` до `_previous_day7` дают прогноз за 2..7 суток.
- Для большинства моделей архив начинается с января 2024 года. Для GFS с марта 2021 года (по документации).
- Проверка по запросам 2026-10-19 для точки Москва, шаг два месяца. Первая найденная дата, где `temperature_2m_previous_day1` не пусто:

| Модель | Первая найденная дата |
|---|---|
| `gfs_global` | 2021-05-15 (ближе 2021-03-15 пусто) |
| `ecmwf_ifs025` | 2024-03-15 |
| `icon_global` | 2024-03-15 |
| `best_match` | 2021-05-15 (по сути GFS) |
| `ecmwf_ifs` (9 км) | 2025-11-15 |

- Для 2024-01-10 поле `previous_day1` у всех проверенных моделей пусто, кроме `best_match` в части дней. Начало архива лежит между январём и мартом 2024 года, точную дату не искали. Скрипт начинает `ecmwf_ifs025` с 2024-03-01.
- `ecmwf_aifs025` (модель ИИ) в архиве есть с 2025 года, `previous_day1` проверен только на 2025-03-01.
- Сверка прогноза с фактом, точка Белгород, 2026-01-01 .. 2026-10-12: n = 6840 часов, корреляция 0.9954, средняя абсолютная ошибка 0.85 градуса, смещение +0.06. Прогноз IFS 0.25 против ERA5-Land. Значения правдоподобны для прогноза на сутки.

#### Как читать `previous_day1` честно

- Для часа H суток D берётся прогон, выпущенный за 24 часа до H. Для начала суток D (00:00 Москвы) это прогон не позднее 00:00 суток D-1.
- Модель нагрузки, которая выпускает прогноз в 00:00 суток D, уже знала бы прогон 00:00 суток D. Он даёт горизонт 0..23 часа, а не 24..47 часов.
- Поэтому `previous_day1` слегка пессимистичен. Это безопасная ошибка: мы не даём модели знание, которого у неё не было бы. В статье это нужно записать одной строкой.
- Прогноз и факт имеют разное происхождение (IFS 0.25 и ERA5-Land). Ошибка прогноза включает разность сеток. Это нужно сказать в разделе об ограничениях.

#### Периоды

| Период | Что есть | Вывод для опытов |
|---|---|---|
| до 2021-05 | только факт | прогноза температуры нет |
| 2021-05 .. 2024-02 | факт и GFS | прогноз только от GFS |
| с 2024-03 | факт, GFS, IFS 0.25, ICON | прогноз IFS полный |

Тестовый период `configs/ru.yaml` (2025-07 .. 2026-06) целиком попадает в зону полного прогноза. Окна ретроспективной проверки до года назад (2024-07 и позже) тоже попадают.

## 4. Узлы и точки

### 4.1. Колонки

| Колонка | Смысл |
|---|---|
| `node_id` | узел иерархии, для которого считается температура |
| `level` | 0 корень, 1 ОЭС или страна, 2 субъект или зона |
| `parent`, `hier` | родитель и иерархия (`ru` или `eu`) |
| `node_name` | русское название узла |
| `leaf_id` | лист, из которого взят город |
| `city`, `lat`, `lon` | город (название GeoNames), координаты геокодера Open-Meteo |
| `weight` | вес города в узле, сумма по узлу равна 1 |
| `population` | население по GeoNames |
| `point_id` | ключ точки загрузки, `широта_долгота` с двумя знаками |
| `has_load` | 1, если по субъекту есть нагрузка в списках АТС |
| `ats_name` | имя субъекта в списках АТС для сопоставления |

Заголовки на английском, чтобы код читал их без переименования. Это отличается от записи в задании (город, широта, долгота, вес). Смысл тот же.

### 4.2. Как считается вес

1. Для листа берутся 1..3 крупных города. Население города берётся из GeoNames через геокодер Open-Meteo.
2. Вес города равен его населению, поделённому на сумму по городам листа.
3. Для узла с детьми берутся города всех листьев под ним. Вес равен населению города, поделённому на сумму по всем этим городам. Это среднее по населению. Температура ОЭС и ЕЭС считается из тех же загруженных точек, отдельная загрузка не нужна.

Ограничения метода.

- Вес по трём городам занижает долю пригородов. Пример: в Московской энергосистеме Москва получает вес около 0.9, хотя в области живёт ещё около 8 млн человек. Разница температур между Москвой и пригородом мала. Для статьи это допустимо, но надо сказать.
- Город не равен энергопотреблению. Тяжёлая промышленность (Норильск, Братск) не следует за населением. Для температуры это второстепенно.
- Координаты города могут отличаться от узла сетки ERA5-Land до 0.05..0.1 градуса.

## 6. Время и формат

- Все ряды в UTC, метка в начале часа (`2026-01-01T00:00`). Московское время равно UTC+3 круглый год с 2014 года. В данных СО метка в московском времени, в `parse_so_ups.py` так и записано. При сведении нужно сдвинуть ряд на три часа.
- Для Европы перевод в локальное время зависит от страны и перехода на летнее время. Данные ENTSO-E и energy-charts хранятся в UTC (`timezone=UTC` в `download_europe.py`). Сведение в UTC проще.
- Единицы: градусы Цельсия. Пропуск в файле записан пустой ячейкой.
- Файлы: `data/raw/weather/archive/ГОД/ТОЧКА.csv` и `data/raw/weather/prev_ecmwf_ifs025/ГОД/ТОЧКА.csv`. Колонки `time`, `temperature_2m` или `temperature_2m_previous_day1`.
- Узловые ряды (взвешенное среднее по городам) строит команда `--aggregate`. Результат `node_temperature_archive.csv.gz`.

## 7. Запасной источник: Copernicus CDS, ERA5

Нужен, если Open-Meteo закроет доступ или лимит помешает. Проверено по странице cds.climate.copernicus.eu/how-to-api (2026-10-19). Сам запрос данных не выполнялся, ключа нет.

Действия человека.

1. Зарегистрируйтесь на cds.climate.copernicus.eu и войдите в аккаунт.
2. Откройте страницу "How to API" и скопируйте блок с адресом и ключом.
3. Сохраните блок в `~/.cdsapirc` на маке. Вид блока: строка `url: https://cds.climate.copernicus.eu/api` и строка `key: <личный токен>`.
4. Откройте страницу набора данных ERA5 (single levels или ERA5-Land) и примите условия лицензии внизу формы. Без этого скачивание не пойдёт.
5. Установите клиент на маке в venv: `pip install "cdsapi>=0.7.7"`.

Заметки.

- Название набора для ERA5 на одном уровне: `reanalysis-era5-single-levels`, для ERA5-Land: `reanalysis-era5-land`. Название проверено по цитате страницы Muñoz-Sabater (DOI наборов 10.24381/cds.e2161bac и 10.24381/cds.68d2bb30 относятся к ERA5-Land). Точное имя набора для запроса копируйте кнопкой "Show API request code" на странице набора.
- Страница how-to-api не указывает пределов на размер запроса. Реальные очереди CDS не проверялись.
- CDS отдаёт сетку, а не точки. Придётся скачать регион (Россия и Европа) и выбрать ближайшие узлы сетки. Это тяжелее, чем Open-Meteo. Скачивать только на маке.
- Прогноз задним числом CDS не даёт. Для него запасной источник в этом документе не проверен.

## 8. Риски для статьи

- Прогноз температуры есть только с 2024-03 (IFS) или 2021-05 (GFS). Опыт с длинным окном в годы до 2024 нельзя вести на прогнозе. Либо опыт ограничен периодом с 2024, либо в более ранних годах берётся факт, и это надо оговорить.
- Модель `ecmwf_ifs025` у Open-Meteo со временем меняет версию. Ряд неоднороден. Документация Historical Forecast API предупреждает об этом, для Previous Runs предупреждение явно не найдено.
- Часть предобученных моделей (Chronos-2) принимает ковариаты. Если дать им температуру как ковариату, надо давать прогноз, не факт. Иначе результат нечестный.
- Население как вес не отражает потребление. Рецензент может спросить про выбор станций. Ответ: ссылка на Hong, Wang, White (2015) и абляция по числу точек.
- Правило Open-Meteo "некоммерческое использование". Статья в журнале не коммерческая, но условие нужно упомянуть в разделе данных.

## 9. Как повторить

Все команды на маке, через `nice`.

```
ssh mac
cd /Volumes/pr/bmstu/papers/soglasovanie-prognozov
python3 src/build_weather_points.py        # таблица точек (лёгкий, можно и на vpnvm)
nice /opt/homebrew/bin/python3.12 -u src/download_weather.py --out data/raw/weather
nice /opt/homebrew/bin/python3.12 -u src/download_weather.py --out data/raw/weather --aggregate archive
nice /opt/homebrew/bin/python3.12 -u src/download_weather.py --out data/raw/weather --aggregate prev_ecmwf_ifs025
```

Повторный запуск продолжает с места остановки. При суточном лимите скрипт выходит с кодом 75. Запускайте его снова после 00:00 UTC (03:00 по Москве). Чтобы скачать прогноз GFS, добавьте `--model gfs_global` и `--plan "prev:2026,2025,2024,2023,2022,2021"`.
