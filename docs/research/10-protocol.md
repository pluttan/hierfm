# Протокол оценки и требования журналов

Дата: 2026-10-19. Документ сверен с кодом `hierfm/evaluate.py`, `metrics.py`, `stats.py`, `report.py`, `data.py`, `dependence.py` и с `configs/suites/*.yaml`.

Пометки в тексте:

- Проверено: факт взят с официальной страницы или из статьи, которую открыл автор документа.
- Не проверено: данные из стороннего источника или из памяти. Перед подачей откройте руководство журнала.

## 1. Ретроспективная проверка

### 1.1. Что сделано в коде

- Скользящее начало прогноза (rolling origin). Начало прогноза ставится в `origin_hour: 21` по UTC, то есть в 00:00 по Москве. Шаг равен `origin_step: 24` часа.
- Горизонты: `horizons: [24, 168]`, то есть сутки и неделя. Прогноз почасовой.
- Тестовый период: с 2025-07-01 по 2026-06-30. В `configs/ru.yaml` он назван предварительным.
- Окна ковариации: `windows: [7, 14, 28, 91, 365]` дней. Для окна берутся ошибки базовой медианы на прошлых началах, цель которых уже известна: условие `opos + h <= pos`.
- Холодный старт: `history_days` обрезает историю узла до 7, 14, 28 или 91 суток.
- Приор метода A строится только по данным до `test_start` (функция `bottom_prior`).
- Страты: праздники (список `holidays`) и самые холодные 10% дней (`cold_quantile`).

### 1.2. Протокол для статьи

1. Базовые модели не дообучаются. Для них «обучающей» выборки нет, есть только контекст `context` часов.
2. Разделите период на два блока. Блок отладки: до 2025-06-30. Блок теста: тест целиком, настройки в нём не менять.
3. Все гиперпараметры (окна, `prior.rho`, `prior.own`, `prior.mix`, число выборок) подберите на блоке отладки. Результаты `prior` и `context` в статье показывайте как анализ чувствительности, не как выбор лучшего значения по тесту.
4. Для недельного горизонта начала идут ежедневно, горизонты перекрываются. Укажите это в тексте и учтите в тесте значимости (раздел 3).
5. Основное окно в отчёте: 28 суток (`MAIN_WINDOW_DAYS`). Статья о короткой истории: главная таблица должна быть для 7 и 28 суток, а не для 365.

### 1.3. Утечки: что проверить

| Источник | Состояние в коде | Что сделать |
|---|---|---|
| Погода | `data.future_temp` при отсутствии `temp_fc` молча берёт фактическую `ds.temp` | Заменить на ошибку. Иначе основной сценарий `issued` может незаметно стать сценарием `actual` |
| Окно ошибок | Условие `opos + h <= pos` исключает неизвестные цели | Корректно. Добавить тест в `tests/test_core.py` на сдвиг начала |
| Шаблон Шааке | `anomaly_template`: `starts` не доходят до `pos - H`, целевые часы известны | Корректно. Проверить тестом, что ни один час шаблона не лежит после `pos` |
| Приор по погоде | Берёт 365 суток до `test_start`, не обновляется внутри теста | Корректно, но консервативно. Написать это в тексте |
| MASE-масштаб | Считается по контексту до `pos` | Корректно |
| GBM | Обучается через `fit(ds, train_end)` | Проверить, что `train_end` не позже `test_start` минус максимальный горизонт |
| Предобучение моделей | Тестовый год мог попасть в данные предобучения | См. ниже |
| Праздники | Список фиксированных дат без переносов выходных | Заменить на календарь с переносами за 2025-2026 годы |

Утечка через предобучение нельзя исключить полностью. Рецензенты спросят об этом первыми. Меры:

- Найдите в карточках моделей дату среза данных предобучения (Chronos-2, TimesFM 2.5, TimesFM 3.0, Moirai-2). Эта дата не проверена автором документа.
- Если тест начинается раньше среза, назовите это ограничением. Покажите отдельно последние три месяца теста, которые лежат после среза.
- Сравните с моделью без предобучения (`snaive`, `gbm`). Разница между согласованием и базой не зависит от утечки так сильно, как абсолютная точность.
- Данные СО ЕЭС публичны и могли попасть в корпуса предобучения. Проверьте перечень корпусов в статьях моделей.

## 2. Метрики

### 2.1. Что есть в коде

| Метрика | Реализация | Замечание |
|---|---|---|
| MAE, MASE | `mase_scale` по сезону 168, среднее по контексту | Масштаб считается по хвосту контекста, не по всей обучающей истории. При холодном старте масштаб шумный |
| CRPS | `metrics.crps`, форма по выборкам с сортировкой | Это V-статистика со знаменателем `K**2`. Она смещена на порядок `1/K`. Честная (fair) версия делит на `K(K-1)` |
| `crps_scaled` | CRPS, делённый на масштаб MASE узла | Основной показатель в отчёте |
| Покрытие и ширина | `coverage`, уровни из `cfg.coverage` | Ширина масштабируется на MASE |
| Energy score | `energy_score`, второй член по половинам выборки | Считается внутри одного уровня иерархии, не по всей иерархии |
| Variogram score | `variogram_score`, порядок 0.5, без весов | Внутри уровня. Веса не заданы |
| PIT | Функция `pit` есть | В `evaluate.py` не вызывается, в `report.py` нет гистограмм |

### 2.2. Чего не хватает

1. RMSSE. Метрика нужна в связке с MASE для точечной оценки: в IJF её ждут из-за соревнований M5. Добавьте `rmsse = sqrt(mean(e^2) / mean(d^2))`, где `d` сезонная разность.
2. Pinball loss на фиксированных квантилях. CRPS можно посчитать как среднее pinball по уровням. Это даёт сопоставимость с работами по квантильным прогнозам.
3. Winkler score или interval score для интервалов 80% и 95%. Покрытие одно само не различает узкий и широкий интервал.
4. PIT и надёжностная диаграмма. Для сценариев удобна гистограмма рангов. Добавьте строку `pit` в `evaluate.py` и таблицу в `report.py`.
5. Энергетический и вариограммный баллы по всей иерархии (все узлы разом). Сейчас они считаются по уровню. Согласование влияет на связи между уровнями, поэтому для главного утверждения нужна оценка по всем 1 + 7 + число субъектов узлов.
6. Вес вариограммы. Для узлов разного масштаба используйте масштабирование по MASE (уже есть) и проверьте устойчивость к порядку `p` в 0.5 и 1.
7. Честный CRPS. Либо смените знаменатель, либо покажите, что при `K = 200` вывод не меняется (эксперимент `samples` уже есть).
8. Агрегирование по уровням. Сейчас уровни показаны отдельно. Добавьте итог по иерархии: средневзвешенное по доле нагрузки и невзвешенное по узлам. Объясните выбор весов.
9. Энергия: у энергетического балла малая чувствительность к ошибкам зависимости (Pinson, Tastu 2013, рабочий отчёт DTU; существование подтверждено по ссылкам в статьях, сам отчёт не открыт. Статья arXiv 1910.07325 оспаривает вывод: мерой чувствительности служит тест DM, и по нему energy score различает модели хорошо). Поэтому variogram score нужен рядом с ним. Это довод для основной таблицы.

### 2.3. Агрегирование

- Сначала усредняйте по часам горизонта, затем по началам, затем по узлам уровня.
- Сообщайте метрики для трёх групп: верх (ЕЭС), ОЭС, субъекты.
- Для относительных величин берите геометрическое среднее отношений (skill score к базе), не среднее процентов.
- Для сравнения методов используйте относительный показатель `метод / mint_shrink` и `метод / base`.

## 3. Значимость

### 3.1. Что есть

- `stats.diebold_mariano`: тест Диболда и Мариано с поправкой Харви, Лейбурна и Ньюболда (HLN), двусторонний, распределение Стьюдента с `T-1` степенями. Параметр `h` задаёт число ковариаций автоковариации.
- `stats.mcb`: ранги и критическое расстояние Немени для множественного сравнения с лучшим.
- `report.py`: DM для пары `prior_shrink` против `mint_shrink` по CRPS и MCB для верхнего уровня.

### 3.2. Замечания к реализации

1. В `report.py` передаётся `h = max(1, h // 24)`. Для суточного горизонта `h = 1`, автоковариация не учитывается. При ежедневных началах разности потерь автокоррелированы (погода, режим сети). Используйте оценку Ньюи и Веста или `h = 2..3` как проверку устойчивости.
2. Для недельного горизонта `h = 7` при `T` около 365 начал. Поправка HLN для таких `h/T` заметна, и это правильно. Укажите её в тексте.
3. DM сравнивает две модели по одному ряду потерь. По узлам и уровням проверок много. Нужна поправка на множественность: Холм или Бенджамини и Хохберг по семейству «модель, горизонт, уровень, окно».
4. MCB строится по рангам начал, которые считаются независимыми. Для автокоррелированных потерь критическое расстояние занижено. Либо прореживайте начала (каждое седьмое), либо используйте блочный бутстреп.
5. Тест Немени и MCB (Demšar 2006; Koning и др. 2005, M3) сравнивают методы по набору случаев. Здесь случаи это начала. Для сравнения по узлам возьмите случаи «узел и начало» и ранжируйте внутри них.
6. DM использует потерю CRPS по узлу. Для совместного прогноза сравнивайте ещё и energy score на уровне всей иерархии (тест DM для многомерных баллов).

### 3.3. Чего не хватает

- Набор уверенных моделей (Model Confidence Set, MCS) Хансена, Лунде и Нейсона (2011). Он отвечает на вопрос «какие методы нельзя отличить от лучшего». Реализация нужна в `stats.py`. Библиотеки `arch` на pcomp нет, ставить нельзя. Напишите бутстреп-версию на `numpy` (блочный стационарный бутстреп, статистика `T_max`).
- Блочный бутстреп для доверительных интервалов разностей метрик.
- Тест Кларка и Веста не нужен, модели не вложены. Тест Джакомини и Уайта нужен, если оценка идёт по скользящему окну: он проверяет условную предсказательную способность. Для статьи достаточно DM.
- Поправка Холма.
- Относительные доверительные интервалы для таблиц (бутстреп по началам).

### 3.4. Что ждут в IJF

- Тест значимости разницы прогнозов с учётом зависимости потерь. Обычно DM с HLN или MCB/MCS. Проверено только по практике статей IJF, жёсткого требования в руководстве автор не нашёл.
- Описание данных, кода и воспроизводимости (раздел 4).
- Сравнение с сильными эталонами: `snaive`, ETS/ARIMA, MinT-shrink, независимые прогнозы без согласования.

## 5. Типичные замечания рецензентов

Список составлен по практике рецензирования статей о нагрузке и по критике моделей-основ. Прямых отчётов рецензентов автор не видел. Это ожидаемые замечания, не цитаты.

Статьи о прогнозе нагрузки:

1. Слабые эталоны. Требуют сравнения с `snaive`, ETS, ARIMA, градиентным бустингом на календаре и погоде.
2. Неясная постановка: что известно в момент прогноза (погода, праздники). Нужна таблица признаков по моментам.
3. Утечка информации из будущего. Особенно через фактическую погоду вместо прогнозной.
4. Короткий тест. Один год не покрывает все режимы. Нужны страты: зима, лето, праздники, аномальный холод.
5. Одна метрика. Требуют точечные и вероятностные метрики вместе.
6. Нет теста значимости или тест без учёта автокорреляции.
7. Отсутствие воспроизводимости: нет кода, версий, зёрен.
8. Подбор параметров на тесте.
9. Одна страна и одна иерархия. Для этого в проекте есть Европа.
10. Не показана практическая польза: что даёт диспетчеру улучшение CRPS на единицы процентов.

Статьи о моделях-основах (foundation models):

1. Утечка из предобучения. Модель могла видеть тестовые ряды.
2. Нечестное сравнение: эталонные модели обучены на малой выборке, модель-основа на огромной. Нужна сильная эталонная модель, настроенная на тех же данных.
3. Воспроизводимость: версии весов, контекст, число выборок, генерация сценариев.
4. Вероятностные прогнозы: калибровка сценариев по узлам и связь между узлами. Это прямо основа метода B.
5. Стоимость вычислений и время работы.
6. Отсутствие абляций: длина контекста, размер модели (в наборе есть `context`, `model_size`).
7. Тест на разных масштабах и в разных странах.
8. Сравнение с бенчмарками: GIFT-Eval (Aksu и др. 2024, Salesforce AI Research, arXiv 2410.10393; существование проверено поиском), Chronos (Ansari и др. 2024, TMLR).

## 6. Итог: что добавить в код

Первая очередь (до написания результатов):

1. `data.future_temp`: ошибка вместо подстановки факта.
2. `metrics.py`: RMSSE, pinball, interval score; честный CRPS как вариант.
3. `evaluate.py`: PIT-гистограммы; energy и variogram по всей иерархии.
4. `stats.py`: Холм, блочный бутстреп, MCS.
